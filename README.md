# edt-branch-sender

Плагин 1C:EDT для переноса изменений задачи в базу, где нет EDT. По одной кнопке он:

1. берёт объекты, изменённые в текущей ветке относительно `develop`;
2. выгружает их в XML формата конфигуратора через штатный экспорт EDT;
3. упаковывает в zip и отправляет в отдельную ветку git (`packages`).

Оттуда пакет забирает и загружает частичной загрузкой автоматизация DevOps. Zip вручную никуда носить не
нужно, полная выгрузка конфигурации тоже не нужна.

## Требования

- 1C:EDT 2025.2 (на других версиях не проверялся — см. «Если что-то не так»).
- Git for Windows, настроенный так, что `git push` в репозиторий проекта проходит без вопросов
  (обычно это уже так: учётные данные хранит Git Credential Manager).
- Проект открыт в EDT из рабочей копии git (обычная схема работы).

## Установка

1. Закрыть EDT.
2. Скопировать `plugin\edtbranchsender_<версия>.jar` из этого репозитория
   в каталог `dropins` установки EDT. Для EDT, установленной через 1C:EDT Start, это:
   ```
   %LOCALAPPDATA%\1C\1cedtstart\installations\1C_EDT 2025.2\1cedt\dropins
   ```
   Каталога `dropins` нет — создать.
3. Запустить EDT. В «Окно → Параметры» появится раздел **«Пакет изменений»**.

**Обновление:** закрыть EDT, удалить из `dropins` старый `edtbranchsender_*.jar`,
положить новый, запустить EDT. **Удаление:** закрыть EDT, удалить jar из `dropins`.

## Ветка пакетов (один раз на репозиторий)

Пакеты складываются в отдельную ветку репозитория проекта — пустую, без исходников и без общей истории с
ними. Плагин её не создаёт: если её ещё нет, её создаёт один человек, остальные просто указывают имя.

Пустую ветку `packages` удобнее всего создать из отдельного пустого репозитория — рабочая копия проекта
при этом не затрагивается:

```
git init C:\temp\packages-init
git -C C:\temp\packages-init commit --allow-empty -m "Ветка пакетов изменений"
git -C C:\temp\packages-init push <URL репозитория проекта> HEAD:refs/heads/packages
```

В Git Bash пути пишутся с прямой косой чертой: `C:/temp/packages-init`. После push каталог можно удалить.
Проверить: в списке веток проекта появилась `packages` с одним пустым коммитом. Merge request для неё
создавать не нужно.

Ветка без файла `.gitlab-ci.yml` не запускает пайплайн GitLab (если путь к конфигурации CI не
переопределён в настройках проекта).

## Первая настройка

«Окно → Параметры → Пакет изменений»:

| Поле | Что указать |
|---|---|
| Проект EDT | проект конфигурации из списка (если он один — уже выбран) |
| Сравнивать с | `origin/develop` |
| Репозиторий | `origin` |
| Ветка пакетов | `packages` |

«Применить и закрыть». Настройки запоминаются, повторно их вводить не нужно.

## Как отправить пакет задачи

1. Переключиться на ветку задачи (`feature/...`), закоммитить работу.
2. **Подтянуть свежий `develop` в ветку задачи** (merge `origin/develop` или rebase) и разрешить
   конфликты, если будут. Без этого отправка недоступна — почему, см. ниже.
3. Открыть «Окно → Параметры → Пакет изменений», нажать **«Обновить»** и убедиться:
   - «Ветка задачи» — нужная ветка;
   - «Синхронизация» — «содержит origin/develop».
4. Нажать **«Отправить»**. Ход виден в журнале под кнопкой, обычно занимает до минуты. Страницу можно
   закрыть — итог придёт сообщением.
5. В итоге в журнале: `Отправлено: packages/feature/TASK-123.zip (коммит …)` и состав пакета.

Повторная отправка той же ветки перезаписывает её пакет; прежние версии остаются в истории ветки
`packages`.

### Что попадает в пакет

- Объекты, изменённые в ветке задачи с момента ответвления от `develop`, плюс незакоммиченные правки
  (флажок «Включать незакоммиченные правки», включён по умолчанию).
- Объект выгружается **целиком**: описание, модули, формы, макеты.
- Из корня конфигурации — только `Configuration.xml` (в нём регистрируются новые объекты). Модуль
  приложения, сеанса и прочие модули конфигурации — только с флажком «Включать модули конфигурации».
- **Удалённые объекты** частичная загрузка не удаляет: они перечислены в `info.txt` пакета, удалять их в
  базе нужно вручную.
- Только конфигурация, не данные: настройки, константы, элементы справочников заводятся отдельно.

### Почему ветка должна содержать свежий `develop`

XML объекта и `Configuration.xml` берутся целиком из ветки задачи. Если ветка отстала от `develop`,
загрузка пакета откатила бы на базе чужие правки тех же объектов, а объекты, добавленные в `develop`
позже, выглядели бы удалёнными. Поэтому:

- страница показывает «отстаёт от origin/develop на N коммит(ов)» и кнопка «Отправить» неактивна;
- перед отправкой плагин делает `git fetch` и проверяет снова — если в `develop` за это время что-то
  слили, отправка откажет с той же подсказкой.

В пакет записывается **коммит базы** — коммит `develop`, с которым ветка синхронизирована. По нему
DevOps могут привести базу к нужному состоянию, если между отправкой и загрузкой `develop` ушёл вперёд.

## Если что-то не так

| Сообщение | Что делать |
|---|---|
| «отстаёт от origin/develop на N коммит(ов)» | подтянуть `origin/develop` в ветку задачи, нажать «Обновить» |
| «Ветка сравнения не найдена» | проверить поле «Сравнивать с» (`origin/develop`) |
| «В рабочей копии есть незакоммиченные правки…» | выключен флажок «Включать незакоммиченные правки» при грязной рабочей копии: закоммитить или включить флажок |
| «Рабочая копия не на ветке (detached HEAD)» | переключиться на ветку задачи |
| «Изменённых объектов нет» | ветка не отличается от `develop` — отправлять нечего |
| «Не удалось получить ветку packages…» | проверить поля «Репозиторий» и «Ветка пакетов»; ветка должна существовать на сервере |
| «В ветке … лежат исходники проекта» | в «Ветка пакетов» указана рабочая ветка (например, `develop`) — указать `packages` |
| push отклонён / ошибка авторизации | проверить, что обычный `git push` из рабочей копии проходит |
| раздела «Пакет изменений» нет в параметрах | плагин не загрузился: причина — в «Окно → Показать панель → Журнал ошибок» или в `.metadata\.log` рабочей области |

Ошибки отправки также пишутся в журнал ошибок EDT.

## Как это устроено

- Список объектов — из git: `git diff --name-only origin/develop...HEAD` и `git status`; путь
  `src/<Каталог>/<Имя>/…` превращается в объект, тип — из заголовка `<Имя>.mdo`.
- XML — штатным экспортом EDT, но только по этим объектам (мастер «Экспорт» умеет только полную
  выгрузку). Содержимое берётся из открытого проекта, то есть из файлов рабочей копии, — поэтому
  отправляется всегда текущая ветка.
- Ветку `packages` плагин держит в собственном неглубоком клоне в
  `<рабочая область>\.metadata\.plugins\edtbranchsender\outbox`; рабочая копия проекта не
  переключается и не меняется. Push — системным git с вашими учётными данными.

## Пакет для загрузки (для DevOps)

**Ветка `packages`:** пакет ветки задачи лежит по пути `<имя ветки>.zip` (`feature/TASK-123` →
`feature/TASK-123.zip`; символы `\ : * ? " < > |` заменяются на `_`). Каждая отправка перезаписывает
файл отдельным коммитом. Сообщение коммита: `<ИД>: пакет <ГГГГММДД_ЧЧММ>`, далее ветка, коммит исходников,
база сравнения и строка `Коммит базы: <хеш>`.

**Внутри zip:**

| Путь | Что это |
|---|---|
| `xml\` | XML изменённых объектов в формате выгрузки конфигуратора (версия формата — в `info.txt`) |
| `info.txt` | UTF-8 с BOM: ветка, коммит, база, коммит базы, формат, список объектов; блок `ВНИМАНИЕ` — удалённые объекты |

**Коммит базы** (`Коммит базы: <полный хеш> от ДД.ММ.ГГГГ ЧЧ:ММ`) — коммит `origin/develop`, который ветка
задачи содержала при отправке. Пакет гарантированно ложится на базу, собранную из этого коммита.

Список файлов для `-listFile` в пакет не входит: это все файлы под `xml\` с абсолютными путями (UTF-8),
строится после распаковки.

**Загрузка** (пакетный конфигуратор):

```
1cv8.exe DESIGNER /F <каталог базы> | /S <сервер>\<база>  /N <пользователь> /P <пароль>
  /LoadConfigFromFiles <распакованный>\xml -listFile <список> -partial
  /UpdateDBCfg /Out <лог> /DisableStartupDialogs
```

- Перед загрузкой при необходимости — `/DumpCfg <файл.cf>` для отката.
- `/UpdateDBCfg` требует монопольного доступа к базе.
- Удалённые объекты частичная загрузка не удаляет — их перечисляет `info.txt`.

## Разработка

```
powershell -File build.ps1 [-Install]
```

Компиляция `javac` из JDK 17 комплекта EDT (`C:\Program Files\1C\1CE\components\axiom-jdk-full-17*`)
против jar-ов p2-пула 1C:EDT Start (`%USERPROFILE%\.p2\pool\plugins`), без Maven. Результат —
`dist\edtbranchsender_<версия>.jar` и его копия в `plugin\` (её и ставят пользователи). С `-Install` —
копирование в `dropins` (EDT должен быть закрыт). При изменениях повышать `Bundle-Version` в
`bundle\META-INF\MANIFEST.MF`: EDT кеширует бандл по версии.

| Файл | Роль |
|---|---|
| `bundle\plugin.xml`, `bundle\META-INF\MANIFEST.MF` | описание бандла, регистрация страницы параметров |
| `Activator` | точка входа, доступ к сервисам и экспорту EDT, настройки, журнал |
| `SenderPreferencePage` | страница «Пакет изменений» |
| `PackageSender` | сценарий отправки и проверки |
| `XmlExporter` | git → объекты → XML через экспорт EDT |
| `Git` | запуск git с тайм-аутом, без консольного запроса пароля |

Путь к `git.exe`, если он не в `C:\Program Files\Git\cmd` и не в `PATH`: строка
`-Dedtbranchsender.git=<путь>` в `1cedt.ini`.
